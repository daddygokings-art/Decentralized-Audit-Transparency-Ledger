## What is SLSA?

[SLSA](https://slsa.dev) (pronounced "salsa") is a security framework for improving the integrity of software supply chains. It defines four levels of guarantees:

| Level | Key guarantees |
|-------|----------------|
| 1 | Provenance exists and is generated automatically |
| 2 | Provenance is hosted on a tamper-resistant service |
| **3** | **Hardened build platform, non-forgeable provenance, and isolated build environment** |
| 4 | Reproducible and hermetic builds (currently experimental) |

This project targets **SLSA Level 3**.

## SLSA Level 3 Compliance Summary

| SLSA Requirement | Implementation | Status |
|---|---|---|
| **Provenance exists** | SLSA in-toto attestation (`.intoto.jsonl`) generated by `slsa-github-generator` | ✅ |
| **Provenance is non-forgeable** | Generated by [slsa-framework/slsa-github-generator](https://github.com/slsa-framework/slsa-github-generator) in an isolated job — NOT by repository code | ✅ |
| **Provenance is hosted on tamper-resistant service** | Uploaded to Sigstore Rekor append-only transparency log | ✅ |
| **Build instructions in version control** | All build steps defined in `.github/workflows/slsa-build.yml` | ✅ |
| **Hermetic build** | Network access restricted; `--locked --frozen`; `CARGO_INCREMENTAL=0` | ✅ |
| **Pinned build tools** | Rust 1.85.0 pinned by version; all GitHub Actions pinned by commit SHA | ✅ |
| **Isolated build environment** | Ephemeral GitHub-hosted runner; `step-security/harden-runner` | ✅ |
| **Artifact signing** | Sigstore cosign keyless OIDC signing; no long-lived private keys | ✅ |
| **Reproducible builds** | Two independent builds compared byte-for-byte in `reproducible-build.yml` | ✅ |
| **SBOM** | CycloneDX SBOM generated and signed with every release | ✅ |

### Why use `slsa-github-generator`?

The non-forgeability guarantee at SLSA Level 3 requires that provenance cannot be created by the repository's own workflows. `slsa-github-generator` runs in an **isolated, reusable workflow** that has no access to the repository's secrets or code. It produces the provenance attestation using GitHub's OIDC infrastructure and Sigstore's Fulcio certificate authority, then uploads the signature to Rekor. Even a repository owner cannot forge valid provenance.

## Verifying a Release (Auditors)

### Prerequisites

```bash
# Install cosign
curl -fsSL https://github.com/sigstore/cosign/releases/download/v2.4.3/cosign-linux-amd64 \
  -o /usr/local/bin/cosign && chmod +x /usr/local/bin/cosign

# Install slsa-verifier
curl -fsSL https://github.com/slsa-framework/slsa-verifier/releases/download/v2.7.0/slsa-verifier-linux-amd64 \
  -o /usr/local/bin/slsa-verifier && chmod +x /usr/local/bin/slsa-verifier

# Or let the verification script install them for you:
# ./scripts/verify-artifact.sh --install-tools ...
```

### Quick verification

Download the release assets, then run:

```bash
./scripts/verify-artifact.sh \
  --wasm       audit_ledger.wasm \
  --bundle     audit_ledger.wasm.bundle \
  --provenance audit_ledger.wasm.intoto.jsonl \
  --checksums  wasm-checksums.txt \
  --source     github.com/daddygokings-art/Decentralized-Audit-Transparency-Ledger \
  --tag        v1.2.3
```

### Manual step-by-step verification

#### 1. Verify the SHA-256 checksum

```bash
# Compute:
sha256sum audit_ledger.wasm

# Compare against the published value in wasm-checksums.txt:
grep audit_ledger.wasm wasm-checksums.txt
```

#### 2. Verify the Sigstore cosign signature

```bash
cosign verify-blob \
  --bundle audit_ledger.wasm.bundle \
  --certificate-identity-regexp \
    'https://github.com/daddygokings-art/Decentralized-Audit-Transparency-Ledger/' \
  --certificate-oidc-issuer \
    'https://token.actions.githubusercontent.com' \
  audit_ledger.wasm
```

What this verifies:
- The `.bundle` file contains a valid Sigstore signature covering `audit_ledger.wasm`
- The signing certificate was issued by Fulcio to a GitHub Actions OIDC token
- The token was issued for a workflow in the correct repository
- The certificate and signature are recorded in the Rekor transparency log

#### 3. Verify the SLSA provenance

```bash
slsa-verifier verify-artifact \
  audit_ledger.wasm \
  --provenance-path audit_ledger.wasm.intoto.jsonl \
  --source-uri github.com/daddygokings-art/Decentralized-Audit-Transparency-Ledger \
  --source-tag v1.2.3
```

What this verifies:
- The provenance was generated by `slsa-framework/slsa-github-generator` (not repository code)
- The provenance covers the exact artifact you have (by SHA-256 digest)
- The artifact was built from the specified source repository and tag
- The provenance attestation is signed and recorded in Rekor

#### 4. Verify the SBOM signature

```bash
cosign verify-blob \
  --bundle audit-ledger-sbom.json.bundle \
  --certificate-identity-regexp \
    'https://github.com/daddygokings-art/Decentralized-Audit-Transparency-Ledger/' \
  --certificate-oidc-issuer \
    'https://token.actions.githubusercontent.com' \
  audit-ledger-sbom.json
```

### Reproducing the binary locally

SLSA Level 3 + reproducible builds means you can independently rebuild the binary and confirm it matches the released hash:

```bash
# 1. Clone and check out the exact release commit
git clone https://github.com/daddygokings-art/Decentralized-Audit-Transparency-Ledger.git
cd Decentralized-Audit-Transparency-Ledger
git checkout v1.2.3   # replace with the release tag

# 2. Install the exact pinned Rust toolchain
rustup install 1.85.0
rustup target add wasm32v1-none --toolchain 1.85.0

# 3. Build with the same flags as CI
SOURCE_DATE_EPOCH=0 CARGO_INCREMENTAL=0 RUSTFLAGS="" \
  cargo +1.85.0 build \
    --target wasm32v1-none \
    --release \
    --locked \
    --frozen

# 4. Compare the hash
sha256sum target/wasm32v1-none/release/audit_ledger.wasm
# Should match the SHA-256 in wasm-checksums.txt from the release
```

## Trust Model

```
What you trust:
  ├── GitHub Infrastructure
  │     The ephemeral runner is provided by GitHub. You trust GitHub
  │     does not modify the build environment between job runs.
  │
  ├── Sigstore (Fulcio + Rekor)
  │     You trust that Sigstore's certificate authority (Fulcio) only
  │     issues certificates to valid GitHub Actions OIDC tokens, and
  │     that Rekor's transparency log is append-only and auditable.
  │
  ├── slsa-framework/slsa-github-generator
  │     You trust that this specific version (v2.1.0) of the generator
  │     correctly attests to the build inputs and does not forge
  │     provenance. It is maintained independently of this repository.
  │
  └── The Rust toolchain (1.85.0)
        You trust that rustc 1.85.0 does not introduce malicious code
        during compilation. The toolchain is fetched from
        static.rust-lang.org via TLS.

What you do NOT need to trust:
  ├── Repository contributors / maintainers
  │     Provenance is generated outside repository control.
  │     Sigstore bundles are anchored in an external transparency log.
  │
  └── This repository's GitHub Actions workflows
        The provenance job runs in an isolated, external workflow.
        Repository code cannot forge the provenance attestation.
```

## Supply Chain Threat Model

The following threats are explicitly addressed:

### T1 — Malicious source code

**Mitigation:** The SLSA provenance attestation records the exact source commit SHA. Any deployed binary can be traced back to a specific commit for code review.

### T2 — Compromised build process

**Mitigation:**
- All build steps are defined in version-controlled workflow files.
- `step-security/harden-runner` restricts egress and syscalls.
- `--locked --frozen` prevents dependency substitution during build.
- The build runs on an ephemeral, freshly-provisioned GitHub runner.

### T3 — Dependency confusion / supply chain injection

**Mitigation:**
- `Cargo.lock` pins all transitive dependency versions.
- `--locked` makes `Cargo.lock` authoritative; build fails if it doesn't match.
- `--frozen` prevents any network-based dependency resolution during build.
- `cargo deny` enforces the license and crate allowlist at CI time.
- `cargo audit` scans for known RustSec advisories.

### T4 — Forged provenance

**Mitigation:** Provenance is generated by `slsa-github-generator`, which runs in a separate reusable workflow with no repository secret access. The attestation is signed with an OIDC-bound certificate that includes the workflow's identity. Any forgery attempt would produce a different certificate identity that `slsa-verifier` would reject.

### T5 — Tampered artifact after build

**Mitigation:**
- Sigstore cosign bundles record the SHA-256 digest and are stored in Rekor.
- Any post-build modification changes the digest, breaking signature verification.
- The SLSA provenance also records the expected digest.

### T6 — Build tool substitution

**Mitigation:**
- The Rust toolchain version (`1.85.0`) is pinned in the workflow.
- All GitHub Actions are pinned by commit SHA, not mutable tags.
- The `cosign` and `slsa-verifier` binaries are verified by SHA-256 before use.

### T7 — Insider threat (maintainer key compromise)

**Mitigation:**
- Sigstore uses **keyless** OIDC signing — there are no long-lived private keys to steal.
- Certificates are valid for only 10 minutes and are bound to a specific GitHub Actions run.
- Every signature is publicly recorded in Rekor; any signing event is auditable.

### T8 — Non-reproducible build artifacts

**Mitigation:**
- `reproducible-build.yml` performs two independent builds and compares them byte-for-byte.
- `SOURCE_DATE_EPOCH=0` and `CARGO_INCREMENTAL=0` eliminate common sources of non-determinism.
- Any party can re-run the build locally and verify the hash.

## FAQ

**Q: Why Sigstore keyless signing instead of a GPG key?**

Long-lived GPG keys become a high-value attack target. If a maintainer's key is compromised, all past and future signatures are suspect. Sigstore keyless signing issues short-lived certificates (10 minutes) tied to a specific GitHub Actions OIDC token. There is nothing to steal; the transparency log provides an auditable history.

**Q: How do I verify the signing identity includes the exact workflow?**

The cosign bundle's certificate contains an extension that records the full workflow ref and job. You can inspect it:

```bash
cosign verify-blob \
  --bundle audit_ledger.wasm.bundle \
  --certificate-identity-regexp '.*' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  audit_ledger.wasm 2>&1 | jq .
```

**Q: What does "non-forgeable provenance" actually mean?**

It means that even if an attacker gains full write access to this repository (including all workflow files and secrets), they cannot generate a valid SLSA Level 3 provenance attestation for a binary they built outside of `slsa-github-generator`. The provenance is signed with an OIDC certificate that identifies `slsa-framework/slsa-github-generator` as the signing identity, not this repository's code.

**Q: Can I verify a pre-release (e.g., `v1.2.3-rc.1`)?**

Yes. SLSA provenance and cosign signatures are generated for all tags matching `v*.*.*` and `v*.*.*-*`. The `--source-tag` argument to `slsa-verifier` must match the exact tag string.

**Q: Where are the signing certificates stored?**

In the [Sigstore Rekor](https://rekor.sigstore.dev) public append-only log. You can search by artifact digest at `https://search.sigstore.dev/?hash=sha256:<hex>`.

**Q: What if Sigstore (Fulcio/Rekor) is unavailable?**

Offline verification is possible using a snapshot of the TUF root metadata. The cosign bundle already contains the certificate and signature; Rekor is consulted only for inclusion proof. For air-gapped environments, use `cosign verify-blob --offline`.

**Q: Is WASM reproducibility guaranteed on all platforms?**

Reproducibility is verified on `ubuntu-24.04` with Rust `1.85.0`. Building on macOS or Windows with the same Rust version and flags _should_ produce an identical binary, but this is not currently verified in CI. Cross-platform reproducibility is tracked as a future improvement.
